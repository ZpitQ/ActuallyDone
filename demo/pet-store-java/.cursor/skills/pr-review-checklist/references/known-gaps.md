# 已知缺口（评审时不要重复报）

<!-- 这份清单的作用是保住评审意见的信噪比。
     没有它，每次评审都会把同样几条重复报一遍，久而久之评审意见就没人看了。

     一条一个缺口，必须写清「为什么暂时不修」与「什么时候处置」。
     写不出这两样的，说明它不是「已知缺口」，而是「还没决定的技术债」——
     那应该去开个 issue，不是记在这里。 -->

## 模板

```markdown
### <缺口一句话>

- **现状**：现在是怎么做的
- **为什么暂时不修**：<成本 / 优先级 / 依赖某个前提>
- **处置计划**：<里程碑或条件，例如「接入 CI 后一并处理」>
- **登记时间**：YYYY-MM-DD
```

## 复核

每个迭代结束时过一遍这份清单：处置条件已经满足的，要么修掉，要么改写理由。
一条缺口在这里躺过三个迭代还没动静，就该重新评估它到底是不是「可接受」。
