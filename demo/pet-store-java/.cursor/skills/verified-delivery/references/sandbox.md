# 沙箱与合并策略

「沙箱后合并」是这套流水线的目标态：实现类 Subagent 在隔离环境里干活，
拿 diff 与真实测试日志换取合并权。有 git 与没 git 是两套做法。

## 有 git：沙箱后合并（推荐）

1. 实现类 Subagent 在**独立 worktree + 独立分支**中工作，互不踩踏。
2. 合并前必须提供两样东西：`git diff` 与**真实测试运行日志**（不是转述）。
3. 由人工或 Reviewer Subagent 看过 diff 与日志后才合并，避免「代码能跑但没测」混进主分支。
4. 有 CI 后，把 verify 段交给 CI：**CI 绿灯才允许合并，Agent 不再自证**。
   这是唯一能真正做到「回执不可伪造」的形态——执行者是 Agent 无权写入的第三方。

## 没有 git（或不便开分支）：证据优先

改动前后各留一份可比对的事实，评审看事实不看自述：

1. **改动前**基线：跑一次 `adone gate run`，记下回执 ID、失败用例数与覆盖率。
2. **改动后**再跑一次，比对同样三个数字。
3. 交付时同时给出：改了哪些文件、前后两份回执 ID、后一次的完整失败清单（应为空）。

覆盖率**掉了**而作者说「只是重构」，是需要追问的信号：重构不该让覆盖率下降。

## 并行 Subagent 的隔离

没有 worktree 时，用这两条降低互相踩踏：

- **按文件分工，不按功能分工**。给每个 Subagent 一份明确的「你可以改这些文件」清单，
  重叠文件由主 Agent 串行处理。
- **有状态的依赖要分开**：并行跑测试时用不同的测试数据库/端口/临时目录，
  否则互相清场，会看到大量莫名其妙的失败。

判定失败归属：把自己的测试单独跑一遍，确认失败是否依然存在，再下结论。
「A 报告的失败其实是 B 正在改同一个文件导致的」是并行开发里最常见的误判。
