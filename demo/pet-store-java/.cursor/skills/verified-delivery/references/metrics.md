# 效果衡量指标

沉淀技能的目的是让经验进入系统而非停在个人身上，所以要能被度量。
下列指标按「引入前 / 引入后」对比看趋势，单次数值没有意义。

## 交付质量

- **千行代码线上 Bug 率**：`区间内线上 Bug 数 / 区间内新增代码千行数`。
- **AI 生成代码首次通过门禁的比例**：Subagent 首次提交即满足全部验收标准的比例。
  **这是最直接反映技能是否起作用的指标**——技能有效，首次通过率应上升。
- **覆盖率变化**：每次交付后记录 `adone gate check` 里的覆盖率，掉线即回归。

## 协作效率

- **Code Review 平均耗时与来回轮次**：从提交评审到通过的时长、被打回的次数。
  评审清单的作用是让问题在第一轮就被指全，轮次应下降。
- **能力复用率**：新成员（或新会话的 Agent）完成同类任务所需时间。
  这是判断「经验是否真正沉淀到系统」的关键指标——如果新人仍要靠口口相传才能上手，
  说明技能没写到位。

## 技能触发准确率（必须人工抽样）

技能最常见的失效方式不是内容错，而是**触发不准**：该加载时没加载，或不该加载时抢占上下文。
这一项静态检测查不了，只能抽样。

做法：每个技能人工抽样 **10~20 次**真实会话，逐次判定：

- **正确触发**：任务确实需要该技能的知识，且它被加载了。
- **过度触发**：任务不需要它却被加载（症状：上下文被稀释，回答里塞进无关约束）。
- **漏触发**：任务需要它却没加载（症状：Agent 犯了技能里已经写明的错误）。

触发准确率 = 正确触发 / 抽样总数。低于 80% 就要动 `description`：漏触发时补触发词与场景词，
过度触发时缩窄场景描述或改成 `disable-model-invocation: true` 只允许显式调用。

### 抽样记录模板

```markdown
## <技能名> 触发准确率抽样（YYYY-MM）

| 序号 | 会话任务简述 | 是否应触发 | 是否实际触发 | 判定 |
| --- | --- | --- | --- | --- |
| 1 | <任务> | 是 | 是 | 正确 |
| 2 | 改 README 错别字 | 否 | 是 | 过度触发 |

准确率：__/__ = __%
处置：<改了 description 的哪一句 / 无需处置>
```

## 记录位置

抽样结果与指标快照追加到本文件末尾，或按月单独建文件放同目录。
**不要只在会话里说一次**——度量数据不落盘，等于没度量。
