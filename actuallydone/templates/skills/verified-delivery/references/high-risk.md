# 高风险模块与额外验证

有些模块出错的后果是**资金偏差、数据偏差或不可逆的线上动作**，单元测试通过不足以放行。
这份清单要你自己填——它的价值恰恰在于内容是本项目踩出来的。

## 清单（按本项目实际情况替换）

一条写一个模块：路径 + 错了会发生什么后果。典型的高风险类别：

- **金额与多币种计算**：错了直接影响成交价与对账。
- **库存 / 唯一编码分配**：一码多用、超卖不可逆。
- **对外发布边界**：唯一真正对外发请求的地方，发出去就收不回。
- **并发队列与调度**：并发下互相覆盖，单次调用测不出来。
- **权限决策**：错了是越权。

```
- **<模块名>**：`<路径>`。<出错后果，一句话>
```

## 额外验证要求

改动上述模块时，除常规验收外还需要：

1. **集成用例覆盖并发路径**：不能只测单次调用的正确性，要测「同一资源两个请求同时来」的结果。
2. **边界值用例**：金额取 0、负数、极大值；数量取 0 与超上限；枚举取范围外的值。
3. **幂等用例**：同样的输入连跑两次，断言副作用只发生一次（或按业务定义的粒度只发生一次）。
4. **贴出运行日志**：这几个模块的用例输出必须原样贴出，不接受转述。

## 端到端可视验证

若当前会话可用浏览器自动化（Playwright / 浏览器 MCP）：

- 对用户**直接读数**的页面，跑一次端到端并**截图**，确认页面上的数字与库里一致。
- 截图随交付一起给出，嵌在回复里。

若浏览器自动化不可用：

- 改用「API 层集成用例 + 贴日志」替代，并在交付说明里注明「未做可视验证」，
  不要默认页面也是对的。**后端对但前端读错字段**是很常见的一类漏网之鱼。

## 不要做的事

- 不要在这些模块上用「mock 掉依赖后单测通过」当作放行依据——并发与分配的问题恰恰出在真实竞争上。
- 不要为了让用例通过而放宽断言（把「至多一条」改成「至少一条」这类）。断言改弱要单独说明理由。
